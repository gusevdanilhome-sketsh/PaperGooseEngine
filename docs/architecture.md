# Архитектурное решение (ADR) — Фаза 0

## Контекст
Разрабатывается 2D-игровой движок на чистом C (стандарт C11) с приоритетами: производительность, безопасность (MISRA-подобный стиль), минимализм и русскоязычная экосистема. Фаза 0 охватывает создание ядра (ECS) и демонстрационного приложения.

## Принятые решения

### 1. ECS на разреженных множествах (Sparse Array)
- Сущность — uint32_t.
- Компонент хранится в массиве, индексированном entity ID.
- Пул компонента содержит presence-маску и выделяется лениво.
- **Почему**: простота реализации, предсказуемость времени доступа O(1). На раннем этапе кэш-промахи некритичны. В будущем возможен переход на архетипы (как в Flecs) для улучшения локальности данных.

### 2. Управление памятью
- Используются безопасные обёртки `mem_alloc`/`mem_free` с проверкой на NULL и аварийным завершением.
- Сборщик мусора отсутствует, управление временем жизни — явное.
- В будущем добавится арена/стековый аллокатор для компонентов.

### 3. Графическая подсистема
- В качестве бэкенда выбран SDL2 + SDL_image. Это кроссплатформенная, зрелая библиотека.
- В Фазе 1 рендерер будет заменён на собственный (OpenGL 3.3+), но SDL останется для окна и ввода.

### 4. Безопасность кода (MISRA-подобные правила)
- Запрещены макросы (кроме include guards и стандартных). Константы задаются через `enum`.
- Все функции проверяют входные указатели.
- Используются типы фиксированной ширины из `<stdint.h>`.
- Явные приведения типов через (int) и т.п.
- Компиляция с флагами `-Wall -Wextra -Wpedantic -Werror`.
- Динамическая память выделяется через обёртки, которые завершают программу при ошибке.

### 5. Система ресурсов
- Простой менеджер текстур с загрузкой через SDL_image.
- Ресурсы идентифицируются целыми числами (индексы в массиве).

## Последствия
- Положительные: быстрое прототипирование, лёгкая отладка, соответствие стандартам безопасности.
- Отрицательные: низкая локальность данных при большом количестве сущностей; необходимость рефакторинга ECS в будущем.
